## 1. DB design review (full)

Two model families were intended: a `TimestampedUUIDBase` for mutable/operational entities
(Booking, Trip, TripItem, TripPlaceLink, SavedPlace) and natural-key `Base` for the 13
reference/seed tables. (Note: §0 — this split is currently being changed.)

### 🔴 Actual bugs / risks
1. **`confirmation_code` lookup key is not unique.** `booking_service.get()` treats the
   derived 6-char code as an alternate lookup (`get_by_confirmation_code` → `.first()`),
   but `ix_bookings_confirmation_code` is non-unique. A hash collision → `.first()` returns
   the wrong booking. The code is deterministic: `short_code_for(id)`, 6 chars over a
   31-char alphabet (31⁶ ≈ 887M). → see §2 (decision: unique + collision-retry).
2. **`TripPlaceLink.added_at` (String) duplicates the base `created_at` (DateTime).**
   `crud/trip.py` still stamps/sorts on `added_at`. Consolidate onto `created_at`.
3. **Soft-delete vs idempotency_key.** Partial unique index is `WHERE idempotency_key IS
   NOT NULL` — does NOT exclude `deleted_at IS NOT NULL`. A soft-deleted row keeps its key.
   BUT: bookings `cancel()` sets `status='cancelled'`, not `deleted_at`, so for bookings
   this path is **not currently reachable**. → decision: keep current (no-op, §2).

### 🟡 Improvements
4. **No FKs on the operational graph.** `TripItem.trip_id/place_id/booking_id`,
   `TripPlaceLink.trip_id/place_id`, `Booking.reference_id` are bare `String`. Only
   `trip_id → trips.id` is a clean FK candidate (orphaned trip_items possible); the
   polymorphic ones can't be FKs. Deliberate "manual joins, no ORM relationships" choice.
5. **`City.country` FKs to `countries.name`, not PK `countries.code`.** Works (backed by a
   unique index) but FKing on the name is the more fragile of the two available keys;
   `country_code → countries.code` sits unused as a constraint. (May be moot after the
   uuid-base refactor demotes these keys.)
6. **Money as `Float`** (`total_price`, `price_per_night`). Fine for a no-payments mock;
   `Numeric(10,2)` is the correctness-safe choice for the canonical `total_price`.
7. **Date consistency.** `Trip.start_date/end_date` stay `String` after timestamps moved to
   real `DateTime`. Consistent only if treated as opaque date tokens.
8. **UUID-as-`String`.** Cross-engine-safe but misses Postgres native `uuid`;
   `sa.Uuid(as_uuid=False)` maps to native uuid on PG / CHAR(32) on SQLite, same str API.

### Must-do (narrow)
- #1 — decide confirmation_code uniqueness (service already relies on it). **Decided: B.**
- #3 — confirm idempotency/soft-delete intent. **Decided: A (keep current).**

## 2. Intake + decisions

- **Lane:** high-risk (uniqueness/migration hard gate + client-visible lookup behavior).
- **Confidence:** low → escalated (both items were decisions, not crisp asks).
- **E1 (#1 confirmation_code):** **B — unique index + collision-retry.** Make
  `ix_bookings_confirmation_code` unique (partial, `WHERE confirmation_code IS NOT NULL`),
  and make booking-id minting collision-aware: mint UUID, derive code, regenerate if the
  derived code already exists. (A plain unique index alone is wrong — the code is *derived*,
  so a collision would surface as a booking-creation `IntegrityError`, not a clean dedupe.)
- **E2 (#3 idempotency):** **A — keep current (no-op).** Reused keys return the existing
  booking; bookings never set `deleted_at` today, so the "burned key" scenario is
  unreachable for bookings. No migration, no code change.

## 3. #1 implementation recipe (apply once the branch settles)

Files: `app/db/models/booking.py`, `app/services/booking_service.py`, one Alembic migration
(or just let an autogenerate/squash pick up the model change, as happened this session).

**a) Model** — make the index unique + partial, mirroring `ix_bookings_idempotency_key`:
```python
Index(
    "ix_bookings_confirmation_code",
    "confirmation_code",
    unique=True,
    sqlite_where=text("confirmation_code IS NOT NULL"),
    postgresql_where=text("confirmation_code IS NOT NULL"),
),
```

**b) Service** (`app/services/booking_service.py`) — collision-aware id minting covering
both `book_flight` and `book_hotel` (both call the id minter then `_repo.add`):
```python
from app.schemas.booking import (
    Booking, FlightBookingDetails, HotelBookingDetails, confirmation_code_for,
)

_MAX_ID_ATTEMPTS = 8  # 31**6 ≈ 887M space; collision is astronomically rare

# inside BookingService:
def _mint_booking_id(self) -> str:
    """Return a fresh UUID whose derived confirmation_code is unused."""
    for _ in range(_MAX_ID_ATTEMPTS):
        booking_id = _new_booking_id()
        code = confirmation_code_for(booking_id)
        if self._repo.get_by_confirmation_code(code) is None:
            return booking_id
    raise RuntimeError(
        f"Could not mint a collision-free confirmation_code after {_MAX_ID_ATTEMPTS} attempts"
    )
```
Then replace both `id=_new_booking_id()` call sites with `id=self._mint_booking_id()`.
`confirmation_code_for(id) = short_code_for(id)` is uppercase; `get_by_confirmation_code`
already `.upper()`s — comparison is symmetric. **Watch the import**: a reformat dropped it
this session, causing `NameError` at `booking_service.py:67`.

**c) Migration** — if migrations are still per-change (not squashed), add one chaining onto
the current head: `op.drop_index("ix_bookings_confirmation_code", table_name="bookings")`
then recreate `unique=True` with the partial predicate; downgrade reverses to non-unique.
Use the partial `sqlite_where`/`postgresql_where` on the drop too. NOTE: this session's
squash auto-absorbed the model change, so a standalone migration may be unnecessary — check
the head migration first.

**d) Tests** (`tests/api/booking/test_bookings.py`):
- `_mint_booking_id` retries past a forced collision (monkeypatch `uuid.uuid4` to yield a
  colliding id then a fresh one; assert the returned id derives an unused code).
- DB rejects a directly-inserted duplicate `confirmation_code` (IntegrityError) — proves the
  unique index.
