## Feature Understanding and Assumptions

- **Requested feature:** per-turn LLM token / cost / latency instrumentation for the LangGraph agent, recorded as one `agent_runs` row per turn via an in-house LangChain callback handler attached in `app/routers/agent.py::_config`; `stream_usage=True` for the OpenAI profile; static USD price table; `usage` on `ChatResponse` and on the `done` SSE event; a `/dashboard/agent-runs` page.
- **What success appears to mean:** after one `/agent/chat` or `/agent/stream` turn, an `agent_runs` row exists with non-zero tokens, a cost, a latency and a per-node breakdown; the client sees the same totals; the dashboard lists the row; the FakeLLM suite proves it offline.
- **Assumptions from the request:** design.md decisions stand (DB table, callback approach, prompt-cache work deferred). This brief supplies evidence, not new design forks.
- **Assumptions still needing confirmation:** (a) whether `trace_id` correlation with Langfuse is required now or can be `handler.last_trace_id` / deferred (design §4.5 assumes `run_id` = trace id, which 4.12.0 does not do); (b) whether Gemini 2.5 Pro's >200k-token tier pricing may be ignored (static per-1M table cannot express it).

## Recommendation

- **Primary recommendation:** Build the thin handler + table as designed (Approach A), with the four corrections below folded into PLAN.md.
- **Why this is the lightest credible path:** callbacks in `config` reach every LLM call in root nodes, sub-graphs, `Send` workers, tools and un-configured nested `llm.invoke()` (contextvars) — confirmed in `_algo.py`, `_runnable.py`, `tool_node.py`; `ainvoke` = `astream` internally so one code path serves both endpoints; `stream_usage=True` is forwarded verbatim by `init_chat_model`; the DB/dashboard/streaming layers all have a template to copy (`ConversationRepository`, `c7f1a9d4e6b2`, `persist_assistant_turn`, dashboard router).
- **Why the next-best alternative lost:** using `UsageMetadataCallbackHandler` as-is loses latency, call count, per-node timing and silently drops calls without `model_name`; parsing the SSE `messages` stream (B) misses `/agent/chat`; wrapping nodes (C) touches 14 nodes + 5 builders and misses structured-output calls — all as design.md already states, now with source evidence.
- **What would change this recommendation:** if the product needed Langfuse-grade per-span traces in-repo (then OTel/Langfuse self-host rather than a summary row), or if `langchain-google-genai` were added and rejected `streaming=True`/usage semantics differed — re-verify at that point.

## Risks, Unknowns, and Follow-Up Questions

- **Technical risks (design.md lines contradicted by evidence):**
  1. **design §4.5** — *"`"run_id": UUID(run_id)` (also makes the Langfuse trace id equal to the row id — free correlation)"*. **Contradicted.** langfuse 4.12.0 `CallbackHandler` never reads `config["run_id"]` as a trace id; the trace id comes from `trace_context={"trace_id": ...}` at construction (the handler is a cached singleton → cannot be per-turn) or the enclosing `start_as_current_observation(...)`; metadata only carries `langfuse_session_id/user_id/trace_name/tags`. Fix: after the run, store `handler.last_trace_id` (public attribute, set on root `on_chain_start`) in a nullable `trace_id` column (feedback-v1 §3.1 wants this column anyway), or wrap the run in `langfuse.start_as_current_observation(trace_context={"trace_id": Langfuse.create_trace_id(seed=run_id)})` when tracing is enabled. Keep `run_id` (it is still the root run id for LangSmith/other tracers; must be a real `uuid.UUID`, and it is stripped from child configs so it cannot collide).
  2. **design §4.3** — *"ChatAnthropic / ChatGoogleGenerativeAI stream usage by default and would reject the kwarg"*. **Half wrong.** `ChatAnthropic` (1.4.7) declares `stream_usage: bool = True` and accepts the kwarg. Google: package not installed; the reference docs list no `stream_usage` field — behaviour on an unknown kwarg is unverified. Keep the `profile.sdk == "openai"` guard (harmless, and it keeps the Google branch untouched), but reword the rationale and the `tests/clients/test_llm.py` assertion ("anthropic profile does not receive the kwarg" is a policy test, not a rejection test).
  3. **design §4.1 table, `on_chain_start/end`** — *"only when `metadata` carries `langgraph_node`: wall-clock per node"*. **Under-specified → double counting.** Task metadata is inheritable: every nested chain run inside a node (and the LLM/tool runs) carries the same `langgraph_node` and `langgraph_checkpoint_ns` (the mapper already reads `langgraph_node` from LLM-chunk metadata). Fix: time only the **first** run seen per `metadata["langgraph_checkpoint_ns"]` (unique per task: `…:<task_id>`) and ignore descendants; sub-graph inner nodes have their own, longer ns (`planner:<id>|assistant:<id>`) so they are still timed separately under `"planner/assistant"`. Also parallel `Send` workers share the node name `synthesis_worker` but differ in ns → design's accumulate-by-name (`runs: 2`) is the right call.
  4. **Team-lead premise / design §4.2 note** — *"Responses API path (gpt-5 family)"*. In this app `ChatOpenAI` selects the Responses API only when `use_responses_api`/`output_version="responses/v1"`/`reasoning`/`include`/`truncation`/`previous_response_id`/built-in tools are set — none are, so gpt-5* runs on **Chat Completions**; `cache_read` comes from `prompt_tokens_details.cached_tokens` (present on both paths). No code change, but the PLAN must not gate anything on "responses".
  5. **design §6 test expectation** — *"`/agent/chat` → `usage.llm_calls ≥ 1`, `input_tokens > 0`"* is satisfiable only through `FakeLLM._generate` calls (sub-agent `assistant`, `summarize`, `reflection`, `synthesize`): FakeLLM's `with_structured_output` returns a `RunnableLambda`, so **supervisor and `resolve_date` structured calls emit no LLM callbacks in tests** — `by_model["fake-llm"].calls` will be lower than the production call count and `by_node["supervisor"]` will show time but zero LLM calls. Document in the test, do not "fix" FakeLLM beyond the design's `usage_metadata`/`response_metadata` addition.
  6. **design §4.1 `on_llm_end` model name** — `on_llm_end` has **no `metadata` kwarg**; `ls_model_name` is only available on `on_chat_model_start`. Keep a `run_id → model` map from start and prefer `response_metadata["model_name"]` at end (as designed); `UsageMetadataCallbackHandler` drops calls lacking either — the in-house handler must count the call regardless and only skip token aggregation.
  7. **Pricing formula** — ignores Anthropic `cache_creation` (1.25× write) and Gemini Pro's >200k tier; acceptable for this spec (no caching yet) but header-document it. `clinepass` model names carry an `openai/` prefix — normalise before lookup.
  8. **Exact-shape tests** — `tests/api/agent/test_stream_events.py:57,68` (`done` payload) and `tests/test_db_models.py:5` (table set) will break on the additive change; both must be in the same task's `<files>`/`<verify>` (docs/solutions/harness/sse-additive-field-breaks-cross-dir-shape-test.md).
  9. **Thread-safety / inline** — sync graph nodes run in worker threads (`copy_context()`), so hooks fire from several threads; `run_inline=True` runs sync hooks on the event-loop thread for async runs — keep hook bodies O(1) and lock-protected as designed.
