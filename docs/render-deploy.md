# Deploying the API on Render

Blueprint: `render.yaml` (repo root). Design: `specs/prod-deploy-render-concurrency/PLAN.md`.
Target: 10 concurrent agent chats; 5 is the floor, scale by adding instances.

## Topology

| Resource | Blueprint name | Notes |
|---|---|---|
| Web service (Docker) | `travel-pi-api` | 2 instances x 2 gunicorn workers = 4 processes. Health check `/readyz`. |
| Background worker | `travel-pi-worker` | Same image, `arq app.worker.WorkerSettings`. Research + memory extraction. |
| Key Value (Redis) | `travel-pi-redis` | Arq queue and research progress pub/sub. `noeviction`, private network only. |
| Postgres | `travel-pi-db` | Paid, >= 1 GB RAM, pgvector. No PgBouncer at this scale. |
| Pre-deploy | `alembic upgrade head` | Runs once per deploy on the web service, not per replica. |
| Env group | `travel-pi-api` | Shared by web and worker. |

Paid plans only. Never deploy this on the free tier (it sleeps).

## Pool budget

Per process: `db_pool_size + db_max_overflow + 2 + db_lock_pool_size` (the LangGraph checkpointer and
store each hold one dedicated connection; each in-flight turn also holds one advisory-lock connection
from its own small pool, never from the request pool). Rule: `total connections <= 0.8 x max_connections`.

| Item | Processes | Per process | Connections |
|---|---|---|---|
| Web (2 instances x 2 workers) | 4 | 5 + 5 + 2 + 5 = 17 (worst case) | 68 |
| Worker | 1 | ~12 | 12 |
| Pre-deploy migration | 1 (transient) | ~1 | ~1 |
| Total | | | about 80 |

So `max_connections` must be at least 100 (80 / 0.8). If the chosen plan allows fewer, set
`DB_POOL_SIZE=3`, `DB_MAX_OVERFLOW=2` and `DB_LOCK_POOL_SIZE=3` in the env group: 4 x 10 + 7 = 47, needing about 59.
Check `SHOW max_connections;` on the provisioned instance before go-live. This is not confirmed from
Render docs; the `plan: basic-1gb` value in the blueprint is a starting point, so verify the plan
name and its limits in the dashboard.
Revisit (PgBouncer, bigger plan) when concurrent users exceed ~30 or when `pg_stat_activity`
exceeds 70% of `max_connections` in a load test.

## LLM concurrency

`LLM_GLOBAL_CONCURRENCY=6` per process gives at most 24 concurrent model calls across the 4 web
processes (the worker has its own semaphore). `AGENT_MAX_CONCURRENCY=3` bounds the specialist
fan-out within one turn. Confirm 24 concurrent calls fits the provider account RPM/TPM tier; lower
the semaphore if not.

## Timeouts

- `GUNICORN_TIMEOUT=180` exceeds the longest LLM call (`llm_timeout_seconds=120`).
- `GUNICORN_KEEPALIVE=75` is above the Render proxy idle timeout, so the proxy never sends on a
  socket gunicorn already closed.
- Research SSE streams must emit events more often than the proxy idle timeout. Verify with a real
  research run in staging. The run itself lives on the worker (up to `research_timeout_s=600`) and
  is not tied to the SSE connection.
- `maxShutdownDelaySeconds` (web 60, worker 120) gives in-flight turns and jobs time to drain on deploy.

## First deploy

1. Dashboard: New > Blueprint, pick the repo and branch.
2. Fill the `sync: false` values:
   - `DATABASE_URL` (web and worker): the database's **internal** URL with the prefix changed to
     `postgresql+psycopg://`. Render shows `postgresql://`, which SQLAlchemy resolves to psycopg2 (not installed).
   - `CORS_ORIGINS`: JSON list of explicit frontend origins, e.g. `["https://app.example.com"]`.
     A wildcard with credentials is rejected in production.
   - `SUPABASE_URL`: the Supabase project URL (`https://<ref>.supabase.co`). Required: the API verifies
     access tokens against its JWKS, and without it every authenticated route returns 401 while `/readyz`
     still passes. Self-hosted Supabase: set `SUPABASE_JWKS_URL` and `SUPABASE_JWT_ISSUER` instead.
   - `DASHBOARD_BASIC_USER` and `DASHBOARD_BASIC_PASSWORD`: the admin dashboard login. The dashboard fails
     closed (unusable) while either is unset. `DASHBOARD_SECRET_KEY` is generated by Render.
   - `OPENAI_API_KEY` (or the key for the chosen `LLM_PROVIDER`), `ANTHROPIC_API_KEY`, `ORS_API_KEY` as needed.
3. Enable the `vector` extension if the first migration does not (`CREATE EXTENSION IF NOT EXISTS vector;` via `psql`).
4. Enable daily backups on the database.
5. Deploy. The pre-deploy step migrates; web instances go live when `/readyz` returns 200.

## Verify (staging)

```bash
curl -fsS https://<service>.onrender.com/healthz
curl -fsS https://<service>.onrender.com/readyz   # {"status":"ready",...}
```

Worker logs should show Arq starting and connecting to Redis. In `psql`,
`SELECT count(*) FROM pg_stat_activity;` should stay under 70% of `max_connections` under load.

## Load test

`apps/api/scripts/loadtest_chat.py` (`make -C apps/api loadtest ARGS='...'`) fires N concurrent
chats with a keyless FakeLLM and reports p95, peak `pg_stat_activity`, 429 and 5xx counts, and a
thread cross-talk check. Mirror the fleet with `--processes 4` against Postgres:

```bash
make -C apps/api loadtest ARGS='--concurrency 5 10 20 --processes 4 --database-url postgresql+psycopg://travel:travel@localhost:5433/travel'
```

Local result (Postgres 17, `max_connections=100`, pool 5+5, 4 processes): 10 chats gave 0 5xx,
p95 0.34 s, 22 peak connections, 0 cross-talk. The thread advisory-lock connection comes from a
separate per-process pool (`DB_LOCK_POOL_SIZE`) and is acquired in the threadpool, so a single
process serving all 10 chats no longer exhausts the request pool or blocks the event loop. To check
an uneven split, run the same command single-process (omit `--processes`).

## Operations

- Scale web: raise `numInstances` or `WEB_CONCURRENCY`, then redo the pool budget above.
- A Redis restart loses queued jobs and live progress only; jobs are idempotent by `run_id` and
  `ResearchService.sweep_stale` recovers stuck runs.
- Rollback: redeploy the previous image from the Render dashboard. Migrations are additive.
- Secrets live only in the dashboard. Rotate there; never commit them.
