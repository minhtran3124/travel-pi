# Travel-PI → Agent-Ready Improvement Plan

A deep analysis of where the codebase is and where it could go to better support an LLM agent doing tool-calling. Grouped by impact.

> **Status refresh (2026-06-25):** This doc was originally written against an earlier
> snapshot. Since then a wave of work landed (`trips`, `visa`, `currency`, `destinations`,
> `air-quality` routers; error `hint` field; short codes; field descriptions). Since the
> 2026-06-17 refresh, **budget endpoints (#12, PR #8)** and **symmetric flight booking
> inputs (#9)** shipped, and field descriptions on the newer schemas (#6) are now complete.
> Items below are tagged so an agent doesn't re-implement what already ships.
>
> **Legend:** ✅ Done · 🔶 Partial (primitive shipped, value-layer open) · ⬜ Not started

## Current state (one-line)

Solid mock REST API with deterministic generation, clean layering, typed schemas. The
UI-vs-agent gap has **narrowed** — a trip grouping primitive, recovery hints, human-friendly
codes, rich field descriptions, the trip value-layer (`total_spent` / `gaps` / day-plan),
and per-category **budget** caps (#12) are all in. What remains is the **agent-orchestration
layer**: quote-then-book, composite `/agent/*` endpoints, an MCP wrapper, and the last small
trip rollup (`remaining_budget`, #1 — now unblocked by #12).

## Tier 1 — High leverage for tool-calling (biggest impact, lowest cost)

### 1. ✅ Trip / Itinerary value-layer — DONE

The grouping primitive ships and **the computed value-layer is now complete**
(`app/routers/trips.py`, `app/services/trip_service.py`, `app/schemas/trip.py`):

- ✅ `GET /trips/{id}` returns computed `total_spent` (`TripDetail.total_spent`,
  `app/schemas/trip.py:138`), `gaps` (`app/schemas/trip.py:141`, e.g. "Day 3 has no
  accommodation"), and now **`remaining_budget`** (summed budget caps − `total_spent`, null
  when uncapped; `app/services/trip_service.py` `get_trip_detail`) — reuses the #12 caps so
  budget headroom is available in one call. Spec `specs/trip-remaining-budget/`.
- ✅ Trip items link to a `booking_id` (`TripItemCreate.booking_id`, `app/schemas/trip.py:38`),
  so booked spend rolls into `total_spent`.
- ✅ `GET /trips/{id}/day-plan?date=YYYY-MM-DD` ships (`app/routers/trips.py:86`) — ordered
  items with travel time between them (`travel_to_next_minutes` / `travel_to_next_mode` via
  `routing_service`, `app/services/trip_service.py:205`) plus a `weather_score` per day (#14).

Nothing left here — the `remaining_budget` rollup on `TripDetail` shipped once #12 provided
the stored caps it depended on.

### 2. ⬜ Quote / Hold before confirm

Both `POST /flights/book` and `POST /hotels/book` commit immediately (no `/quote` exists).
Agents work best with a two-step flow:

- `POST /flights/quote` → returns a `quote_id` valid for N minutes with locked price + the full booking details echoed back
- `POST /flights/book` accepts either current params *or* a `quote_id`
- Same for hotels

This lets the agent show the user "here's what I'm about to book" before paying the cost of an irreversible action — the same pattern Claude's tool-calling UX wants.

### 3. ⬜ Batch / composite operations

Agents loop a lot; each loop is a round-trip and a chance to derail. Add:

- `POST /agent/plan` — input: `{origin, destination, start_date, end_date, adults, preferences?}` → output: top 3 flight options + top 3 hotel options + 5 recommended places + weather summary + key tips, all in one response
- `POST /bookings/batch` — array of flight/hotel booking requests, all-or-nothing or partial-success modes, idempotency keys per item

`/agent/plan` is the single most useful endpoint you could add: it collapses 5+ tool calls into 1 and gives the agent a coherent starting context.

### 4. ⬜ Tool-manifest / discovery endpoint

- `GET /agent/manifest` — a curated list of tools with **agent-flavored descriptions** ("Use this to find flights between two airports on a specific date"), example inputs, and "when to use this" / "when NOT to use this" notes. Generated from a hand-written manifest, not autogenerated from OpenAPI (which is too verbose and missing the "when").
- `GET /places/categories`, `GET /places/cities` already exist — extend the pattern: `GET /agent/airlines`, `GET /agent/amenities`, `GET /agent/tip-categories` so the agent can enumerate valid filter values without guessing.

### 5. ⬜ MCP server wrapper

The natural form factor for a tool-calling agent is **MCP**, not raw HTTP. Add a thin `app/mcp/` module (or a separate `mcp_server.py`) that exposes the most useful endpoints as MCP tools with proper descriptions, schemas, and examples. Claude Code / Claude Desktop / Claude Agent SDK can then consume it directly. (The root `.mcp.json` is Claude Code's own client config — it is **not** an exposed server.)

## Tier 2 — Schema & error polish (makes existing tools better, not new features)

### 6. ✅ Rich field descriptions everywhere — DONE

Most Pydantic fields now carry `Field(..., description="…", examples=[…])` across
`place`, `flight`, `hotel`, `weather` schemas (~80%+ coverage). The newer schemas
(`trip`, `visa`, `currency`, `destinations`, `air_quality`) now carry `Field(description=…)`
too — the parity sweep this item flagged is closed.

### 7. ✅ Structured error hints — DONE

The error envelope now carries an optional `hint` (`AppError` in `app/exceptions.py:21`,
emitted by the handler in `app/main.py:84`). **Remaining:** audit that the *raise sites*
actually pass useful hints (e.g. flight/hotel not-found and sold-out paths) — the
mechanism is in place; coverage of good hint text is the follow-up.

### 8. ✅ Confirmation codes everywhere — DONE

Hotels expose a `short_code` (`HTL-…`), places a `short_code` (`PLC-…`), and bookings a
`confirmation_code`; flight IDs remain human-readable (`FL_HAN_BKK_20260601_03`). The raw-UUID
gap this item flagged is closed.

### 9. ✅ Symmetric booking inputs — DONE

`FlightBookingRequest` now accepts a `flight_id` as an alternative to flight_number + route +
date (`app/schemas/flight.py:155`), so an agent can do `search → pick id → book` without
unpacking the ID — mirroring the hotel_id flow. Shipped on `feat/symmetric-booking-inputs`
(spec `specs/symmetric-booking-inputs/`, delivered 2026-06-20).

## Tier 3 — New agent-flavored features

### 10. ✅ Natural-language search shim — DONE

- ✅ `POST /places/search/nl` ships (`app/routers/places.py`). Body `{query: "romantic dinner
  in Hanoi under $40"}` → a pure keyword/regex parser (`place_service.parse_nl_query`) extracts
  `{city, category, min_rating, price_level}` server-side and the response echoes the `parsed`
  filters back alongside matches ("here's how I interpreted you"). No LLM — `re` + the canonical
  `CITIES` list. Budget phrases ("under $40") and adjectives ("cheap") map to a `price_level`
  band applied as a **ceiling** (`<=`). Specs in `specs/places-nl-search/`.

### 11. ⬜ "Travel between" inside a trip

`routing_service` already does place↔place and city↔city. Add:

- `GET /trips/{id}/transit?from_item=…&to_item=…` — uses item start/end times to suggest mode and warn about tight connections ("only 20 min between activities, but routing says 35 min by car")

### 12. ✅ Budget endpoints — DONE

Shipped in **PR #8** (spec `specs/trip-budget/`, 2026-06-19; commits `afff1b3` / `af6362e` /
`63f5e75`):

- ✅ `GET /trips/{id}/budget` (`app/routers/trips.py:128`) — per-category caps (flights /
  hotels / activities / buffer) vs. booked spend, with `total_remaining` and an `over_budget`
  flag (`TripBudget`, `app/schemas/trip.py:302`).
- ✅ `POST /trips/{id}/budget` (`app/routers/trips.py:142`) — replace-semantics setter for the
  caps, stored in the `budget_caps` JSON column (`app/db/models/trip.py:20`).
- ✅ Over-cap enforcement: adding a trip item whose linked booking would push a category past
  its cap returns **409** (`_enforce_budget`, `app/services/trip_service.py:377`). Enforced at
  `POST /trips/{id}/items` (the only trip↔booking link point), not at the trip-unaware book
  endpoints. Covered by `tests/api/trip/test_trip_budget.py` (12 tests).

### 13. 🔶 Visa / docs / currency helpers — currency & visa DONE, entry-requirements shape differs

- **Currency** ✅ — `GET /currency/convert?from=USD&to=VND&amount=100` ships (`app/routers/currency.py`).
- **Visa** ✅ (different shape) — guidance ships at `GET /visa?city=…` / `?country=…`, **not** at
  the proposed `GET /destinations/{country}/entry-requirements`. Note: a `destinations` router
  already exists but covers `GET /destinations/{city}/overview` + `GET /destinations/climate`,
  *not* entry requirements. Decide whether to reshape `/visa` into the structured
  `{visa_required, max_stay_days, passport_validity_months, vaccines[]}` contract or leave as-is.

### 14. ✅ Weather-aware packing & day suitability — DONE

Both pieces shipped (commit `f277111`):

- ✅ `GET /weather/packing?days=N` (`app/routers/weather.py:55`, `days` 1–16) — returns
  clothing/gear suggestions derived from forecast highs/lows/precipitation.
- ✅ `weather_score` (0–1, `None` when unavailable) on each day inside
  `GET /trips/{id}/day-plan` (`DayPlanResponse.weather_score`, `app/schemas/trip.py:170`;
  computed in `app/services/trip_service.py:284`).

### 15. ⬜ Activity booking (places become bookable)

Right now places are discoverable, not bookable. Add `POST /places/{id}/book` with `{datetime, party_size, contact}` → creates a third booking type (`activity`). Mock availability the same way hotels do (deterministic by id+datetime).

## Tier 4 — Robustness & ops (less glamorous, real-world correctness) — ✅ DONE (PR #4)

All five shipped on `feat/tier4-robustness-ops`; specs in `specs/tier4-robustness-ops/`.

- ✅ **Idempotency on mutating endpoints** — `Idempotency-Key` replay added to `POST /trips`
  and `POST /trips/{id}/items` (the non-idempotent creates), mirroring the booking pattern.
  PUT/DELETE/`cancel` are already idempotent by semantics; no `batch` endpoint exists.
- ✅ **Rate-limit headers** — informational, **unenforced** `X-RateLimit-Limit/Remaining/Reset`
  on every response (`app/main.py`; `rate_limit_nominal` setting). Deliberate waiver of the
  "no rate limiting" scope note — no 429s/counters.
- ✅ **`/healthz` / `/readyz`** — `app/routers/health.py`. `/readyz` checks the DB and reports
  the ORS routing provider as a separate non-fatal upstream (`live`/`fallback`); degrades to
  `not_ready` instead of 500 when the DB is down.
- ✅ **OpenAPI `operationId`** — pinned to handler names via one `generate_unique_id_function`
  in `app/main.py` (renamed the `list_cities` collision → `list_place_cities`).
- ✅ **Soft-delete for trips** — `DELETE /trips/{id}` now stamps `deleted_at` and keeps the
  row + items; all trip reads filter `deleted_at IS NULL`. (Was confirmed hard-delete before.)

## Appendix — Current codebase inventory (reference)

### Endpoints today

- **Meta:** `GET /`
- **Cities:** `GET /cities`, `GET /cities/{city_name}`, `GET /cities/route`
- **Airports:** `GET /airports`
- **Flights:** `GET /flights/search`, `GET /flights/{flight_id}`, `POST /flights/book`
- **Hotels:** `GET /hotels`, `GET /hotels/search`, `GET /hotels/availability`, `GET /hotels/{hotel_id}`, `POST /hotels/book`
- **Places:** `GET /places`, `GET /places/search`, `GET /places/cities`, `GET /places/categories`, `GET /places/nearby`, `GET /places/route`, `GET /places/{place_id}`
- **Tips:** `GET /tips`
- **Destinations:** `GET /destinations/{city}/overview`, `GET /destinations/climate`
- **Currency:** `GET /currency/convert`
- **Visa:** `GET /visa` (by `city` or `country`)
- **Weather:** `GET /weather`
- **Air quality:** `GET /air-quality`
- **Bookings:** `GET /bookings`, `GET /bookings/{booking_id}`, `POST /bookings/{booking_id}/cancel`
- **Trips:** `POST /trips`, `GET /trips`, `GET /trips/{id}`, `PUT /trips/{id}`, `DELETE /trips/{id}`, `POST /trips/{id}/items`, `PUT /trips/{id}/items/{item_id}`, `DELETE /trips/{id}/items/{item_id}`
- **Dashboard:** Jinja2 HTML pages (not API)

### Seed data coverage

- 49 cities · 49 airports (1:1) · 154 hotels (≥3/city) · 231 places (≥3/city) · 7 airlines · 14 country tips + 6 city tips
- Invariant `app/core/invariants.py:check_city_coverage()` enforces ≥3 hotels/places per city at startup.

### Persistent state

- SQLite (`travel.db`): `bookings` table + `flight_index` table (resolves deterministic flight UUIDs across restarts) + `trips` table.
- Everything else (flights, hotel availability, places, routes) is generated deterministically from seed data + MD5-seeded RNG.
